# 真实数据接入与独立验收

## 先跑自己的报表

1. 在线私有工作台或`python server.py`打开界面，点击“更换数据”。
2. 选择CSV/TSV/XLSX，确认编码、日期格式、单一币种和销售金额口径。
3. 明确选择“日×分组汇总”或“订单明细（一行一单）”。映射需要的列；多余个人信息不用映射。
4. 订单明细勾选完整导出声明；有状态列时填写纳入状态。不明确的金额口径先询问数据提供者。
5. 点击检查。修复有行号的问题；不能用“汇总重复”掩盖重复导出。仅在缺失确实表示无业务时确认补零。
6. 确认导入，先做“销售金额趋势”或“订单量趋势”，再做相邻窗口比较。数据不足14天时，可选择较短窗口。
7. 导出质量报告、标准数据和分析报告，与原平台的同一日期、状态、币种结果核对。

可尝试最小报表：

```csv
date,channel,revenue,orders
2026-10-01,门店A,1250.00,10
```

这是格式示例，不是真实业务记录；分析最近7天需要完整7天，比较需要14天。用户源数据不需要提交到GitHub。本地默认不落盘；按需下载到自己的受控目录。

## 有来源的公开验收案例

- 作者与引用：Chen, D. (2015). **Online Retail [Dataset]**. UCI Machine Learning Repository. https://doi.org/10.24432/C5BW33
- 官方来源：https://archive.ics.uci.edu/dataset/352/online+retail
- 许可证：[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)。本项目再分发的是经过转换的子集，遵循署名和说明修改的要求；数据许可不等于项目代码许可。
- 原表541,909行，2010-12-01至2011-12-09，英国零售企业交易；UnitPrice单位GBP。InvoiceNo以C开头表示取消。
- 原档与工作簿SHA256、转换规则、来源行数及派生文件哈希记录在`dist/datasets/uci-manifest.json`。

### 转换，不伪造字段

选取2011-11-01至11-30、Country=United Kingdom。78,640个原始商品行中，按顺序排除904行C前缀取消、137行其他非正数量、124行非正单价，纳入77,475行。按InvoiceNo汇总Quantity×UnitPrice并逐发票四舍五入到2位；每张发票只计一单。没有按相似商品行去重，避免误删真实多行交易。

派生为2,490个订单汇总行，再汇总成26个日×地区记录。姓名/CustomerID/商品描述均不发布。地区分组不是营销渠道；没有创造广告成本、点击、注册或支付状态。正向发票销售不是净收入或已支付GMV。

界面案例覆盖整个月。UCI将原档描述为全量交易；据此明确声明4个无正向销售的缺失日为0，报告保留补零数量。真实用户导入时补零默认关闭。

### 核对结果（GBP）

|窗口|正向销售额|校验方法|
|---|---:|---|
|2011-11全月|1,325,346.21|独立Python Decimal分别汇总订单与日汇总|
|2011-11-24至30|277,736.03|共享JS引擎 + Python HTTP入口|
|2011-11-17至23|284,447.21|共享JS引擎 + 自选日期|

这验证真实公开数据的导入与计算路径，不能证明用户自己的报表完整、大模型质量或业务增长。

### 重建公开样例

仅准备数据需要`openpyxl==3.1.5`，应用运行不依赖它：

```bash
python -m pip install openpyxl==3.1.5
# 从UCI官方页面下载online+retail.zip，保存在仓库外。
python tools/prepare_uci.py /absolute/path/online-retail.zip
npm test
python -m unittest discover -s tests -p 'test_*.py' -v
```

原档22MB、54万行，不适合直接扔进浏览器的5MB导入入口。重建脚本读取完整原档，在仓库只保留必要的公开聚合子集。真实大报表同样应先在受控环境按目标粒度/范围聚合，而不是放宽浏览器限制。
